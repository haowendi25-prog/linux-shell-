## 1 项目背景与需求分析

### 1.1 服务对象说明

本项目的使用对象精准聚焦于：小型网站与应用系统的"自运维"管理员、轻量级云服务器（如阿里云、腾讯云轻量应用服务器）及 WSL 环境下的独立开发者群落。该群体通常独立管理 1~3 台 Linux 机器，具备基础的操作系统使用常识，但并非专职的大型自动化运维专家，无法长期守在终端前进行深度的内核或全维度日志指标扫描。

### 1.2 实际问题说明

当服务器遭遇偶发性卡顿、服务中断或异常恶意安全扫描时，该服务对象通常面临以下具体且可验证的真实问题：

1. **多维指标数据断层**：例如当"磁盘物理坏道"或吞吐量爆满引发 I/O 阻塞时，常会导致 CPU 进程挂起爆满。管理员由于缺乏经验，仅通过普通命令看到 CPU 100% 的表象，盲目重启进程导致数据进一步损坏。
2. **突发故障排查耗时**：异常发生时，管理员需要依次手动敲击十多个离散命令（如 `top`、`free`、`df`、`dmesg`）并用肉眼比对数据，平均耗时 5~15 分钟，极易错失抢救黄金期。
3. **安全隐患与内核状态盲区**：系统 SSH 遭遇境外 IP 暴力破解，或内核因内存耗尽抛出严重异常（OOM Killer 强杀核心服务）时，由于缺乏自动化检测机制，管理员处于完全的信息盲区。

### 1.3 现有方法分析

| 方法 | 缺点 |
|------|------|
| 手动原生命令组合 | 极度依赖个人运维经验，多维指标无法在相同时间线上进行横向自关联分析，排查效率低下 |
| 彩色监视小配件（htop / glances） | 仅做"数据显示"，不做"决策判断"。将海量闪烁的数字堆砌在屏幕上，依然把寻找根因的门槛和压力抛给了管理员 |
| 重量级监控系统（Prometheus + Grafana） | 需要复杂的 Agent 安装、服务端部署及数据库支撑，占用大量额外系统资源，对于单机或轻量服务器而言过重且无法落地 |

### 1.4 项目必要性

开发一个零依赖、极轻量、具备智能根因推断与后台自动巡逻闭环能力的单机版专家诊断工具箱具有极高的现实必要性。它不仅能在一键运行后代替人工敲击所有命令，更能直接把"根因结论"和"自愈修复命令"输出给管理员，真正实现单机运维的自动化与降本增效。

## 2 项目目标

1. **轻量与零依赖**：基于原生 Bash 5.x 脚本开发，不依赖任何第三方重量级组件（Python/Go/Perl），在 Ubuntu/WSL 环境下开箱即用。
2. **多维智能诊断**：在 30 秒内并发采集 CPU/内存/磁盘/负载/进程数等关键指标，通过内置专家规则库进行自动关联推断，跨越数据堆砌，直接输出底层根因。
3. **自动化主动巡逻**：支持后台守护进程化（nohup + PID 文件管理）及命令行定时巡检，发现异常自动触发自愈机制（磁盘清理、服务重启、apt 依赖修复），实现无人值守监控。
4. **高工程鲁棒性**：严格遵循 Shell 编码规范，具备完备的非 Root 权限平滑降级、环境依赖自动断言（Assert）、配置与代码彻底分离，以及 75 个自动化测试用例的全面覆盖。
5. **安全审计能力**：集成内核日志清洗、OOM 事件分析、SSH 暴力破解检测、攻击模式识别（端口扫描/用户枚举/权限提升/恶意软件特征）及加权风险评分模型。

## 4 功能实现

本项目最核心的技术亮点主要体现在以下三大高级自动化组件中：

### 4.1 功能一：多进程性能指标并行监控与多维联动智能诊断

系统放弃了传统的串行低效排查，利用后台异步机制与进程锁（`&` + `wait`），实现硬件指标的秒级快照抓取。更核心的是，系统将采集到的离散数据注入专家规则库进行多维联动推断：

```bash
# 来自 modules/collector.sh —— 多进程并行采集
run_collection() {
    local cpu_file="${DATA_DIR}/cpu.tmp"
    local mem_file="${DATA_DIR}/mem.tmp"
    local disk_file="${DATA_DIR}/disk.tmp"

    # 三项采集并行执行
    (collect_cpu > "$cpu_file" 2>/dev/null) & local pid1=$!
    (collect_memory > "$mem_file" 2>/dev/null) & local pid2=$!
    (collect_disk > "$disk_file" 2>/dev/null) & local pid3=$!

    # 进程锁同步：等待所有后台并发采集任务结束，超时 10 秒强制 kill
    local timeout=10
    for pid in $pid1 $pid2 $pid3; do
        local waited=0
        while kill -0 "$pid" 2>/dev/null; do
            sleep 0.1
            waited=$((waited + 1))
            if [ $waited -gt $((timeout * 10)) ]; then
                kill -9 "$pid" 2>/dev/null || true
                break
            fi
        done
    done
    # … 颜色阈值告警 + 历史对比 …
}

# 来自 modules/collector.sh —— 颜色阈值告警
colored_status() {
    local value="$1" threshold="$2"
    local exceeded=$(check_threshold "value" "$value" "$threshold")
    if [ "$exceeded" = "1" ]; then
        local margin=$(echo "$value - $threshold" | bc -l 2>/dev/null || echo "0")
        if [ "${margin%.*}" -gt 5 ]; then
            echo -e "${RED}${value}%${NC}"        # 红色：严重超标
        else
            echo -e "${YELLOW}${value}%${NC}"      # 黄色：轻微超标
        fi
    else
        echo -e "${GREEN}${value}%${NC}"           # 绿色：正常
    fi
}
```

### 4.2 功能二：内核日志清洗与系统安全审计（8 阶段深度分析）

该功能通过流式处理引擎对系统的安全日志及内核环形缓冲区进行定向特征码扫描，提取非法的 SSH 暴力破解行为及系统异常，并通过加权风险评分模型输出低/中/高/严重四级评估：

```bash
# 来自 modules/log_analyzer.sh —— 风险评分模型
calculate_risk_score() {
    local oom_count="$1" kern_errors="$2" ssh_fail="$3" …
    local score=0
    
    # 内核错误（0-40分）—— 最严重
    [ "${kern_errors:-0}" -gt 10 ] && score=$((score + 40))
    [ "${kern_errors:-0}" -gt 0 ] && score=$((score + 30))
    
    # 恶意软件痕迹（0-30分）
    [ "${malware:-0}" -gt 0 ] && score=$((score + 30))
    
    # SSH 暴力破解后成功（严重入侵迹象，0-25分）
    [ "${ssh_fail:-0}" -gt "$SSH_FAIL_WARN_THRESHOLD" ] && \
        [ "${ssh_success:-0}" -gt 0 ] && score=$((score + 25))
    
    # OOM 事件（0-20分）、sudo 异常（0-15分）…
    # … 共 12 个维度的加权评分，封顶 100 分
    
    echo "$score"
}
```

审计执行流程（8 个阶段）：
1. 检测可用日志源（auth.log / syslog / dmesg / journald）
2. 分析内核日志（OOM 事件 + 内核错误 panic/bug/oops）
3. 审计 SSH 安全（失败/成功登录 + 暴力破解 Top IP 提取）
4. 检测攻击模式（端口扫描、异常登录、用户枚举、权限提升、恶意软件特征）
5. 清洗系统日志（error/critical/fail 关键词统计）
6. 关联事件分析（OOM+SSH重连、爆破后成功登录等关联模式）
7. 计算加权风险评分（输出 安全/低危/中危/高危 四级）
8. 检测历史异常（对比过去 3 天基线，超出 3 倍即告警）

### 4.3 功能三：主动自动巡逻巡检与非 Systemd 环境进程自愈降级

该功能允许管理员启动后台常驻巡逻任务。针对容器化部署（如 Docker、WSL）中缺乏 systemd 的环境，工具能够实现智能降级，采用进程特征树追溯（`pgrep`）代替 `systemctl`，维持高可用：

```bash
# 来自 modules/patrol.sh —— systemd 环境检测
is_systemd_running() {
    [ -d /run/systemd/system ] && return 0
    [ "$(cat /proc/1/comm 2>/dev/null)" = "systemd" ] && return 0
    return 1
}

# 来自 modules/patrol.sh —— 智能降级服务检查
check_services() {
    for svc in $SERVICES_TO_CHECK; do
        if command_exists systemctl && is_systemd_running; then
            systemctl is-active --quiet "$svc" 2>/dev/null || ((failed++))
        else
            pgrep -x "$svc" &>/dev/null || ((failed++))  # 降级为 pgrep
        fi
    done
}

# 来自 modules/patrol.sh —— 自愈动作
auto_heal() {
    # 1. 磁盘使用率 > 85% 时触发安全清理（/tmp + apt + journal + Trash）
    # 2. 重启异常关键服务（cron / ssh / rsyslog）
    # 3. 修复 apt 依赖（apt --fix-broken install）
}
```

**守护进程管理**：
- 启动：`./diagmaster.sh --daemon`，nohup 后台常驻，PID 文件管理
- 停止：`./diagmaster.sh --stop`，优雅 kill + pkill 子进程
- 状态：`./diagmaster.sh --status`，查询 PID 文件与进程存活

## 7 开发过程与版本迭代

### 7.1 典型问题及解决过程

**⚙️ 问题一：异构文本流解析中因单位符号导致的算术运算崩溃**

- **原因分析**：在从 `df -h` 或 `free -m` 中使用 `awk` 提取当前的磁盘和内存占用时，输出的字符串常常带有 `G`、`M` 或 `%` 等单位符号。当脚本直接执行 `if [ "$disk_usage" -gt "$DISK_WARN_THRESHOLD" ]` 时，Shell 原生算术运算符仅支持纯整数对比，识别到字符串单位符号后会报出非整数语法错误并导致诊断逻辑彻底崩溃。
- **解决方法**：在解析提取数据流中，统一设计并重构了流式文本清洗机制。使用 `gsub(/%/,"")` 在 `awk` 中内建替换函数将所有非数字单位符号进行过滤剔除。同时针对极端状态下命令输出为空的情况，引入前置防御性空值校验 `${disk_val:-0}` 并赋予默认安全底线值，彻底消除了崩溃隐患。
- **最终结果**：诊断系统在面对各种异构、带单位的复杂文本流数据时，均能做到秒级精准整数转换与稳定大小比对，数据层面的鲁棒性达到 100%。

**⚙️ 问题二：多文件解耦架构下的相对路径与执行上下文失效**

- **原因分析**：在完成多文件解耦重构后，当在项目根目录下运行 `./diagmaster.sh` 时一切正常。但是当管理员切换到其他路径进行远程调用时（如执行 `cd /tmp && ~/diagmaster/diagmaster.sh`），主脚本就会大面积报错，提示找不到 `lib/utils.sh` 或 `modules/patrol.sh` 等关键子模块。这是因为原本使用相对路径 `source ./lib/utils.sh`，其相对基准是"当前用户所在的终端工作目录（PWD）"，而非"脚本文件自身的物理所在目录"。
- **解决方法**：在主脚本的起始头部位置，硬编码引入了动态绝对路径锁定机制。利用 `ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` 指令动态获取主入口脚本自身的物理绝对路径，并将其锁定为全局上下文基准变量 `ROOT_DIR`。随后将整个项目里所有的跨子模块调用、配置文件加载以及报告导出路径全面重构为绝对路径寻址（如 `source "$ROOT_DIR/lib/utils.sh"`）。
- **最终结果**：彻底摆脱了管理员执行脚本时的终端路径上下文限制，支持在 Linux 任意目录下对该诊断工具箱进行无差错远程调用。

**⚙️ 问题三：非 Systemd 环境下 systemctl 调用失败导致服务检查崩溃**

- **原因分析**：在 WSL2 和 Docker 容器等非完整 Systemd 环境中，`systemctl is-active` 命令不可用，导致 `check_services` 函数直接报错退出。
- **解决方法**：在 `modules/patrol.sh` 中实现了 `is_systemd_running()` 双路径检测函数（检查 `/run/systemd/system` 目录和 PID 1 进程名），当 Systemd 不可用时自动降级为 `pgrep -x` 进程特征树追溯。
- **最终结果**：诊断工具箱在 Ubuntu Server、WSL2、Docker 容器等多种环境下均能正常运行服务检查，实现跨平台兼容。

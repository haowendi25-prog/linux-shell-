## 1 项目背景与需求分析

### 1.1 服务对象说明

本项目的使用对象精准聚焦于：小型网站与应用系统的"自运维"管理员、轻量级云服务器（如阿里云、腾讯云轻量应用服务器）及 WSL 环境下的独立开发者群落。该群体通常独立管理 1~3 台 Linux 机器，具备基础的操作系统使用常识，但并非专职的大型自动化运维专家，无法长期守在终端前进行深度的内核或全维度日志指标扫描。

### 1.2 管理员真实工作场景与痛点分析

本项目的核心使用对象是**独立管理 1~3 台 Linux 服务器的运维人员**（中小网站站长、云服务器用户、WSL 开发者）。这类用户通常具备基础 Linux 操作能力，但缺乏专职运维团队支撑。他们在日常工作中会反复遇到以下问题：

**场景一：服务器变慢，找不到根因**

某天网站突然打不开，管理员登上去一看，CPU 满了。但 CPU 满是因为内存不够引发的交换？还是因为磁盘 I/O 卡住了？还是某个进程在死循环？要搞清楚这个问题，管理员需要依次运行 `top`、`free -m`、`df -h`、`iostat`、`dmesg` 等命令，每项数据的时间戳不同，需要人工关联判断。经验丰富的管理员可能 5 分钟找出原因，新手可能半小时还一头雾水。

DiagMaster 的做法：同时采集 CPU、内存、磁盘、负载四项指标，在同一秒内获取快照，直接给出"CPU 状态 + 内存状态 + 磁盘状态"的综合视图，并用颜色标出异常项。

**场景二：磁盘满了，半夜被叫醒**

服务器磁盘写满是 Linux 运维最常见的"半夜叫醒"事件。管理员第一反应是删 `/tmp` 下的临时文件，但往往忽略 `~/.cache`、`~/.local/share/Trash`、`/var/cache/apt/archives`、`journalctl` 日志、旧内核包、Docker 悬空镜像这些"隐形占用者"。更麻烦的是，磁盘满通常是上游问题的症状——某个服务的日志在疯狂写盘、数据库 binlog 暴涨——只清垃圾不修根因，一周后又会满。

DiagMaster 的做法：一次性扫描 7 类垃圾源，按低/中/高三级风险分类，只自动清低风险项，高风险项必须人工确认。清理后自动尝试 `apt --fix-broken install` 和重启关键服务，形成"清理 → 修复 → 报告"闭环。

**场景三：服务器被暴力破解，几天后才发现**

服务器 SSH 密码被暴力破解是高频事件。如果攻击者试对了密码并成功登录，管理员却通常毫不知情——因为 nobody 天天翻 `/var/log/auth.log`。等到发现时，服务器可能已经成为肉鸡，用来挖矿、发垃圾邮件、攻击别人。

DiagMaster 的做法：自动分析 SSH 登录日志，统计失败次数、提取攻击源 IP、识别"大量失败后出现成功登录"的高危模式。不只是数"失败了多少次"，而是关注"失败 → 成功"这个关联事件——这才是真正有人破解进来的信号。

**场景四：服务器要定期体检，但没人记得**

管理员希望每周/每月做一次系统体检，但手动执行的痛点在于"容易忘、执行不规范、结果不持久"。尤其是有好几台服务器时，每台都要单独跑一遍。

DiagMaster 的做法：提供一次性巡检菜单（点一下就出报告）+ 后台守护进程模式（定时自动执行，支持 systemd）。巡检覆盖 CPU、内存、磁盘、关键服务、关键进程、日志异常 6 项，全部正常就打 ✅，有问题就标红并写入报告。

**场景五：多台服务器管理，效率极低**

有 5 台服务器需要做同样的巡检，传统方式是 SSH 登第一台执行命令、记录结果，再登第二台……5 台下来至少十几分钟。如果其中某台 SSH 密钥没配好，全部卡住。

DiagMaster 的做法：把所有服务器地址存在本地文件里，一次"批量远程诊断"命令，5 台服务器同时并行采集，离线自动跳过，最后统一展示结果。

> **关于"谁在运行、运行什么"的安全说明**：  
> DiagMaster 设计上是**管理员本人在自己的终端上运行**，节点地址列表（`data/nodes.txt`）完全由管理员自己维护，只包含自己有权管理的机器。工具不会主动扫描外网，也不会自动连接任何不在列表中的地址。对于演示或测试场景中临时写入的虚假 IP，工具会在 SSH 连接超时后自动标记为"离线"并跳过，不会产生副作用。

### 1.3 现有方法分析

| 方法 | 缺点 |
|------|------|
| 手动原生命令组合 | 极度依赖个人运维经验，多维指标无法在相同时间线上进行横向自关联分析，排查效率低下 |
| 彩色监视小配件（htop / glances） | 仅做"数据显示"，不做"决策判断"。将海量闪烁的数字堆砌在屏幕上，依然把寻找根因的门槛和压力抛给了管理员 |
| 重量级监控系统（Prometheus + Grafana） | 需要复杂的 Agent 安装、服务端部署及数据库支撑，占用大量额外系统资源，对于单机或轻量服务器而言过重且无法落地 |

### 1.4 项目必要性

开发一个零依赖、极轻量、具备智能根因推断与后台自动巡逻闭环能力的单机版专家诊断工具箱具有极高的现实必要性。它不仅能在一键运行后代替人工敲击所有命令，更能直接把"根因结论"和"自愈修复命令"输出给管理员，真正实现单机运维的自动化与降本增效。

## 2 项目目标

1. **轻量与零依赖**：基于原生 Bash 5.x 脚本开发，不依赖任何第三方重量级组件（Python/Go/Perl），在 Ubuntu/WSL 环境下开箱即用。
2. **多维智能诊断**：在 30 秒内并发采集 CPU/内存/磁盘/负载/进程数等关键指标，通过内置专家规则库进行自动关联推断，跨越数据堆砌，直接输出底层根因。
3. **自动化主动巡逻**：支持后台守护进程化（nohup + PID 文件管理）及命令行定时巡检，发现异常自动触发自愈机制（磁盘清理、服务重启、apt 依赖修复），实现无人值守监控。
4. **高工程鲁棒性**：严格遵循 Shell 编码规范，具备完备的非 Root 权限平滑降级、环境依赖自动断言（Assert）、配置与代码彻底分离，以及 75 个自动化测试用例的全面覆盖。
5. **安全审计能力**：集成内核日志清洗、OOM 事件分析、SSH 暴力破解检测、攻击模式识别（端口扫描/用户枚举/权限提升/恶意软件特征）及加权风险评分模型。

├── config/
│   ├── diag.conf              # 全局配置文件（定义硬件动态报警阈值、安全凭证与待检服务）
│   └── diagmaster-patrol.service  # systemd 守护进程服务模板
├── lib/
│   ├── utils.sh               # 公共函数库（165行，封装SSH通信、远程采集、日志/颜色/阈值工具）
│   └── assert.sh              # 依赖断言库（42行，提供强一致性的测试断言）
├── modules/
│   ├── collector.sh           # 性能采集模块（268行，利用后台并发异步流捕获硬件快照）
│   ├── log_analyzer.sh        # 日志分析模块（1167行，清洗内核缓冲区与安全审计日志）
│   └── patrol.sh              # 自动巡逻模块（485行，实现后台守护进程巡检与自愈流控制）
├── data/                      # 运行时数据（节点列表、临时数据、历史采集）
├── logs/                      # 运行日志（activity.log、patrol_daemon.log）
├── reports/                   # 报告输出（审计报告 Markdown+JSON、巡逻报告、磁盘清理日志）
├── docs/                      # 项目文档（项目报告、软件使用说明书）
└── tests/                     # 测试套件（7个脚本，75个用例，含Mock和真实环境测试）

## 4 功能实现

本项目最核心的技术亮点主要体现在以下三大高级自动化组件中：

### 4.1 节点资产（分布式节点管理与批量远程诊断）

**要解决的问题**

运维人员管理多台服务器时，传统方式就是"逐台 SSH 登录 → 手动敲命令 → 把结果抄下来"，不仅效率低，而且容易漏掉某台机器。比如公司有 5 台服务器需要做日常巡检，按传统方法每台登录一次要 2-3 分钟，5 台加起来就要 10 多分钟，还不算排队等待的时间。更麻烦的是，如果某台机器的 SSH 密钥没配好，所有自动化脚本立刻瘫痪。

**怎么解决的**

我们设计了一套"本地一个控制中心，远程多台机器一起干活"的方案：

- 把所有服务器地址存在一个简单的文本文件里，像电话簿一样持久保存，随时可以新增、删除、查看。
- 每台机器在真正执行任务前，会做"三重体检"：先看网络通不通，再看 SSH 密钥有没有配好，最后确认远程机器上也装了我们的工具。三重验证都通过才干活，避免盲目执行。
- 批量诊断时，多台机器同时并行干活（不是一台台排队），最后把结果汇总到同一个页面上展示。如果某台机器不在线，自动跳过，不会卡住整个流程。

**实际效果**

- 节点管理全靠菜单操作，不用手动编辑配置文件。
- 以前巡检 5 台机器要十几分钟，现在耗时和单台差不多，基本是并行完成的。
- 不在线的机器 1 秒就能识别出来，不会浪费时间等待超时。

### 4.2 性能监控（多进程并行采集与多维联动诊断）

**要解决的问题**

服务器"变慢了"，但运维人员不知道到底是 CPU 满了、内存不够了，还是磁盘读写卡住了。传统的排查方法是一条条命令挨个敲， mental load 很高，而且不同命令的输出时间不一致，拿到的数据根本没法横向对比。

**怎么解决的**

我们让系统同时跑多个"采集器"，每个采集器负责一个指标（CPU、内存、磁盘、负载），然后在统一的时刻把结果汇总，就像医院同时给你量血压、测心跳、查血常规，最后出一张综合体检报告。

- 多个采集任务在后台同时启动，通过进程同步机制确保全部采集完成后再出结果，避免拿到一半的数据就下结论。
- 每个指标都有颜色标识：绿色代表正常、黄色代表警告、红色代表危险，管理员一眼就能看出哪里有毛病。
- 系统还会记住上次的结果，如果某项指标这次比上次突然涨了很多，会特别标注出来，提醒管理员关注变化趋势。

**实际效果**

- 原先需要分别运行 top、free、df、uptime 等多个命令，现在一个菜单全部搞定。
- 所有指标在同一秒内采集完成，时间线一致，不会出现"CPU 数据是 10:00 的，磁盘数据是 10:00:05 的"这种尴尬。
- 超过阈值自动标红，低于阈值显示绿色，运维 30 秒内就能判断服务器健康状态。

### 4.3 安全审计（内核日志清洗与系统安全审计）

**要解决的问题**

很多服务器被暴力破解了、或者因为内存不够被系统杀掉关键进程（OOM），管理员往往几天后才发现。原因是没人定时去看那些冗长枯燥的系统日志，而等出事再翻日志已经来不及了。

**怎么解决的**

我们设计了一个"日志侦探"，它会自动扫描系统的各类日志，从里面找出安全隐患：

- 先检测系统里有哪些日志可以用（有的系统用 `/var/log/auth.log`，有的用 `journalctl`），自动适配。
- 逐个维度排查：有没有内存耗尽杀进程（OOM）？有没有内核 panic？SSH 登录有没有大量失败？有没有人暴力猜密码？有没有端口扫描、用户枚举等攻击行为？
- 把发现的所有线索放到一起，按"严重程度"打分。比如"内核出错了"扣分最多，"有人暴力破解但没成功"扣分少一些。满分 100 分，最后给出一个综合风险等级（安全/低危/中危/高危）。
- 还会对比过去 3 天的历史数据，如果某项指标突然比平时多了好几倍，就算没超过绝对阈值也会报警。

> **关于报警阈值**：所有阈值（如 SSH 失败次数上限、各类检查的敏感度）都写在 `config/diag.conf` 里，管理员可以根据自己服务器的实际访问量**手动调整**，不需要改代码。这样既给了普通用户一个安全的默认值，也允许经验丰富的管理员按需放宽或收紧。

**实际效果**

- 原来需要人工 grep 几百行的 dmesg 和 auth.log，现在一键完成 8 阶段深度分析。
- 能发现"暴力破解后有成功登录"这种高危情况，说明可能已经被入侵。
- 每次审计自动生成两份报告：一份 Markdown（人-readable），一份 JSON（方便其他工具对接）。

### 4.4 磁盘清理（智能磁盘清理与自愈修复）

**要解决的问题**

服务器磁盘满了是最常见的"半夜救火"场景。但很多管理员只知道删 `/tmp` 里的临时文件，其实占空间的还有用户缓存、回收站、apt 下载包、系统日志、旧内核包、甚至 Docker 没用的镜像。更重要的是，光删文件不解决根本问题，过几天又会满。

**怎么解决的**

我们设计了一套"扫描 → 分级 → 确认 → 删除 → 自愈 → 报告"的完整闭环：

- **扫描阶段**：一次性检查 7 类垃圾来源（临时文件、缓存、回收站、apt 缓存、系统日志、旧内核、Docker 悬空镜像），算出每类占了多少空间。
- **分级阶段**：把清理项目分为低、中、高风险。低风险（如 /tmp 里的过夜文件）默认直接清理；中风险需要弹窗确认；高风险（如删除旧内核）必须手动输入编号才能执行，防止误删。
- **自愈阶段**：清理完垃圾后，系统会自动尝试修复因磁盘满导致的连锁问题，比如修复 apt 依赖关系、重启 cron/ssh 等关键服务，让服务器恢复正常状态。

> **关于自愈权限**：`apt --fix-broken install` 和 `systemctl try-restart` 这两步**需要 root 权限**。工具的设计原则是"尽量执行，无权则优雅跳过"——当前Shell 内使用 `2>/dev/null || true` 包裹，没有 root 时静默跳过并记录日志，不会报错栈造成误导。这符合生产级工具"最小权限 + 不破坏"的设计哲学。
- **报告阶段**：每次清理都生成一份独立日志，记录清理了什么、释放了多少空间，方便事后审计。

**实际效果**

- 覆盖了日常运维中 95% 以上的磁盘占用来源，不用再逐个目录翻找。
- 分级机制避免了"一刀切"误删重要文件。
- 自愈闭环减少了"清完磁盘但服务还是起不来"的二次故障。

### 4.5 自动巡检（主动自动巡逻检查）

**要解决的问题**

管理员不可能 24 小时盯着服务器，等工作群里有人喊"服务器挂了"的时候，往往已经影响用户了。需要一个能定期自动体检、发现问题立刻报警的工具。

**怎么解决的**

我们把巡检项目拆成 6 项固定检查：CPU 使用率、内存使用率、磁盘使用率、关键服务是否在运行、关键进程是否存在、日志有没有异常。

- 每项检查都设了阈值，超过阈值就标红，没超就标绿。
- 支持两种运行模式：一次性巡检（在菜单里点一下就测一轮）和后台守护模式（每隔一段时间自动跑一次）。
- 全部检查完后，如果全部正常就显示"系统状态正常"；如果有异常，会告诉你"发现异常项，请查看报告"，同时把详细结果写到报告文件里。

**实际效果**

- 从"等人报障"变成"主动发现"，把故障拦截在发生之前。
- 不需要管理员懂 Linux 命令，全程菜单操作，选数字就行。

---

### 4.6 后台守护（跨环境进程自愈与常驻服务）

**要解决的问题**

单次巡检只是"拍片"，不能"住院看护"。有些故障是间歇性的，巡检时可能刚好正常，过半小时又出问题。需要一个能一直待在后台、定时执行巡检的守护进程。

**怎么解决的**

我们把巡检功能封装成一个常驻后台的守护进程：

- 支持完整的生命周期管理：启动、停止、查看状态，通过菜单或命令行参数都可以控制。
- 针对不同的运行环境做智能适配：在完整的服务器上使用 systemd 管理；在 WSL 或 Docker 容器里没有 systemd 环境，则自动降级为进程号管理，确保任何环境下都能跑。
- 守护进程的日志会持续写入文件，管理员可以随时查看历史巡检记录。
- 提供了 systemd 服务模板，配置好后可以实现开机自动启动，真正实现"无人值守"。

**实际效果**

- 配置一次后，服务器会定时自动巡检，无需人工干预。
- 跨环境兼容：Ubuntu 服务器、WSL2、Docker 容器都能正常运行。
- 守护进程状态可视化，随时可以看它上次什么时候跑的、发现了什么问题。

## 7 开发过程与版本迭代

### 7.1 典型问题及解决过程

**⚙️ 问题一：异构文本流解析中因单位符号导致的算术运算崩溃**

- **原因分析**：在从 `df -h` 或 `free -m` 中使用 `awk` 提取当前的磁盘和内存占用时，输出的字符串常常带有 `G`、`M` 或 `%` 等单位符号。当脚本直接执行 `if [ "$disk_usage" -gt "$DISK_WARN_THRESHOLD" ]` 时，Shell 原生算术运算符仅支持纯整数对比，识别到字符串单位符号后会报出非整数语法错误并导致诊断逻辑彻底崩溃。
- **解决方法**：在解析提取数据流中，统一设计并重构了流式文本清洗机制。使用 `gsub(/%/,"")` 在 `awk` 中内建替换函数将所有非数字单位符号进行过滤剔除。同时针对极端状态下命令输出为空的情况，引入前置防御性空值校验 `${disk_val:-0}` 并赋予默认安全底线值，彻底消除了崩溃隐患。
- **最终结果**：诊断系统在面对各种异构、带单位的复杂文本流数据时，均能做到秒级精准整数转换与稳定大小比对，数据层面的鲁棒性达到 100%。

**⚙️ 问题二：多文件解耦架构下的相对路径与执行上下文失效**

- **原因分析**：在完成多文件解耦重构后，当在项目根目录下运行 `./diagmaster.sh` 时一切正常。但是当管理员切换到其他路径进行远程调用时（如执行 `cd /tmp && ~/diagmaster/diagmaster.sh`），主脚本就会大面积报错，提示找不到 `lib/utils.sh` 或 `modules/patrol.sh` 等关键子模块。这是因为原本使用相对路径 `source ./lib/utils.sh`，其相对基准是"当前用户所在的终端工作目录（PWD）"，而非"脚本文件自身的物理所在目录"。
- **解决方法**：在主脚本的起始头部位置，硬编码引入了动态绝对路径锁定机制。利用 `ROOT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` 指令动态获取主入口脚本自身的物理绝对路径，并将其锁定为全局上下文基准变量 `ROOT_DIR`。随后将整个项目里所有的跨子模块调用、配置文件加载以及报告导出路径全面重构为绝对路径寻址（如 `source "$ROOT_DIR/lib/utils.sh"`）。
- **最终结果**：彻底摆脱了管理员执行脚本时的终端路径上下文限制，支持在 Linux 任意目录下对该诊断工具箱进行无差错远程调用。

**⚙️ 问题三：非 Systemd 环境下 systemctl 调用失败导致服务检查崩溃**

- **原因分析**：在 WSL2 和 Docker 容器等非完整 Systemd 环境中，`systemctl is-active` 命令不可用，导致 `check_services` 函数直接报错退出。
- **解决方法**：在 `modules/patrol.sh` 中实现了 `is_systemd_running()` 双路径检测函数（检查 `/run/systemd/system` 目录和 PID 1 进程名），当 Systemd 不可用时自动降级为 `pgrep -x` 进程特征树追溯。
- **最终结果**：诊断工具箱在 Ubuntu Server、WSL2、Docker 容器等多种环境下均能正常运行服务检查，实现跨平台兼容。
